# API and server boundaries

Developer reference for every way into the server: HTTP route handlers, the Razorpay webhook, generated files (manifest, sitemap, robots, icons, share images), the service worker, server actions, the Postgres functions the app calls, and the adapters for external providers.

There is no public JSON API. The browser talks to the server through **server actions** (Next.js `"use server"` functions) and a handful of **route handlers** that return files or receive webhooks. Reads go through Server Components with the user's Supabase session (RLS) or, for privileged reads, the service-role client after a permission check.

Conventions used below:

- **Session** means a Supabase Auth cookie session (`lib/supabase/server.ts`). Route handlers read it with `getSession()` (`lib/auth/session.ts`), which also loads roles, permissions and `profiles.is_blocked`.
- **`assertPermission(key)`** (`lib/auth/guards.ts`) throws `AuthorizationError` when there is no session, the profile is blocked, the permission is missing, or (Phase 11) the user has a verified TOTP factor but the session is still `aal1`.
- **`mutate(key, schema, input, write)`** (`lib/admin/mutate.ts`): `assertPermission` → zod parse → write with the user's client (RLS + audit trigger) → `revalidateTag("catalog")` and revalidate the admin layout. Returns `{ ok: true, id? } | { ok: false, error, field? }`.
- **Service role** means `createAdminClient()` (`lib/supabase/admin.ts`, `server-only`), which bypasses RLS. It is only used after the caller has been authorised in TypeScript.
- Money is integer **paise** everywhere below the UI.

### 1.2 Razorpay webhook

`POST /api/webhooks/razorpay` · Node runtime · `force-dynamic`. The source of truth for payments and refunds (D-035).

**Request**

| Part                   | Meaning                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Body                   | Raw Razorpay event JSON (`{ event, payload: { payment?, refund?, payment_link? } }`)                                |
| `x-razorpay-signature` | HMAC-SHA256 of the raw body with `RAZORPAY_WEBHOOK_SECRET`, compared in constant time (`lib/payments/signature.ts`) |
| `x-razorpay-event-id`  | Deduplication key. If absent, the SHA-256 of the raw body is used.                                                  |

**Events handled**

| Event                                                                    | Action                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payment.authorized`, `payment.captured`, `payment.failed`, `order.paid` | When the payment has an `order_id`: `applyRazorpayPayment()` (`lib/bookings/service.ts`), which captures authorised payments, checks the amount against the order, and calls `record_payment` (idempotent on the provider payment id). A payment that arrives after the hold expired confirms if inventory is free, otherwise it is refunded. |
| `payment_link.paid`                                                      | `applyRazorpayPayment()` with the payment link id (quote and balance links).                                                                                                                                                                                                                                                                  |
| `refund.created`, `refund.processed`, `refund.failed`                    | Finds the `payments` row by `provider_payment_id` and calls `record_refund` (idempotent on `provider_refund_id`). Unknown payment → result `unknown_payment`.                                                                                                                                                                                 |
| anything else / unparseable payload                                      | Stored and marked processed with result `ignored`.                                                                                                                                                                                                                                                                                            |

The Razorpay dashboard should subscribe to `payment.authorized`, `payment.captured`, `payment.failed`, `order.paid`, `refund.processed`, `refund.failed` and `payment_link.paid` (DEPLOYMENT.md §9); `refund.created` is also accepted.

**Idempotency**

1. The event is upserted into `payment_events` on `(provider, event_id)` with `ignoreDuplicates`.
2. If the row already existed and `processed_at` is set, the handler answers `{"status":"duplicate"}` and does nothing.
3. If it existed but was never processed (an earlier attempt failed), processing runs again.
4. Payment and refund functions are themselves idempotent on the provider ids, so two racing deliveries confirm a booking once.
5. On success the row gets `processed_at`, `result` and `booking_id`; on failure it gets `error` and stays unprocessed.

**Responses**

| Status | Body                                       | When                                                                     |
| ------ | ------------------------------------------ | ------------------------------------------------------------------------ |
| 200    | `{ "status": "ok", "result": "<result>" }` | Processed                                                                |
| 200    | `{ "status": "duplicate" }`                | Already processed                                                        |
| 200    | `{ "status": "ignored" }`                  | Signature fine, payload not recognised                                   |
| 400    | `{ "error": "invalid signature" }`         | Bad or missing signature                                                 |
| 400    | `{ "error": "invalid json" }`              | Body is not JSON                                                         |
| 500    | `{ "error": "storage" }`                   | Could not store the event (Razorpay retries)                             |
| 500    | `{ "error": "processing failed" }`         | Processing threw; reported through the error reporter (Razorpay retries) |
| 503    | `{ "error": "not configured" }`            | `RAZORPAY_WEBHOOK_SECRET` (or the Razorpay config) is missing            |

### 1.4 Account export (Phase 11)

`GET /api/account/export` returns everything tied to the signed-in account as a JSON attachment (`lib/privacy/export.ts`, format and file name in `lib/privacy/assemble.ts`): profile, addresses, travellers, wishlist, bookings, prescriptions, reviews, points ledger, referrals and leads. Data is read with the service role, scoped to the session's user id. Each successful download calls `log_data_export`.

| ------ | ------------------------------------------ | --------------------------------------------------------------------- |
| 200    | JSON file, `no-store, private`             | OK                                                                    |
| 401    | `{ "error": "signin" }`                    | No session or blocked profile                                         |
| 403    | `{ "error": "mfaRequired" }`               | User has a TOTP factor but has not entered a code                     |

### 1.5 Maintenance preview (Phase 11)

`GET /api/security/maintenance-preview?next=<path>[&exit=1]`. When the `site.maintenance_mode` flag is on, the public layout renders the maintenance page (`lib/security/maintenance.ts`). This route lets staff see the real site: signed-out callers are redirected to `/login?next=…` and back; a signed-in, unblocked user with at least one admin module permission gets Next draft mode, then is redirected to `next` (same-origin only, `safeNextPath`). `exit=1` disables draft mode. Non-staff are simply redirected.

## 2. Server actions by module

All actions take a single `unknown` input that is parsed with zod on the server and return a typed result object (`{ ok: true, … } | { ok: false, error }`); none throw to the client for expected failures. "Permission" is the key checked with `assertPermission` / `mutate`. "Session" means any signed-in, unblocked user acting on their own rows. "Token" means the no-login link token is the only credential.

## 3. Postgres functions

All functions live in `public`, use `set search_path = ''`, and most are `SECURITY DEFINER`. Execute rights fall into four groups:

- **service_role only**: revoked from `public`, `anon`, `authenticated`, granted to `service_role`. Called from `lib/**` with `createAdminClient()` after a TypeScript permission check. Staff-initiated calls pass `p_actor` (or call `set_actor`) so the audit trigger records who did it.
- **authenticated**: callable by any signed-in user through PostgREST.
- **RLS helpers**: used inside policies; left executable by `anon` / `authenticated` (or `authenticated` only where noted) because policies run as the caller. They only return booleans or ids.
- **Trigger only**: never called through the API (execute revoked or irrelevant; triggers fire regardless).
