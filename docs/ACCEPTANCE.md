# Acceptance criteria

How each criterion from the master build prompt (§15) is checked. "Automated" means it runs in CI on every push (`pnpm test` for unit and database tests, `pnpm test:e2e` for the browser tests). "Manual" items need the live site with real keys.

| #   | Criterion                                                                                                                                                                                     | Status                                | Where it is checked                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | Admin can add, edit, delete or hide any hotel, room, rate, cab route / fare, vehicle, coupon, banner, package, menu item and page content, and the public site reflects it without a redeploy | Met                                   | `tests/unit/acceptance-revalidation.test.ts`: each admin action checks its permission, writes, then refreshes the `catalog` cache tag, and public reads are cached under that tag (hotels, cabs, coupons, banners, packages, menu items, CMS FAQ and testimonials); nothing is refreshed when the permission check or the write fails. Manual: DEPLOYMENT §7–§15 smoke tests. Gap: hotels can be exported to CSV but not imported.                                                                                                                                              |
| 2   | A customer signs in with Google or email, books a hotel and a cab, pays with UPI through Razorpay, and sees the booking in My Trips with an invoice                                           | Met in code; needs Razorpay keys live | `tests/e2e/booking.spec.ts`, `cabs.spec.ts`, `account.spec.ts`; `tests/db/bookings.test.ts` (payment capture confirms the booking and issues the invoice). Manual: DEPLOYMENT §9 and §10 with Razorpay test keys (UPI `success@razorpay`).                                                                                                                                                                                                                                                                                                                                      |
| 3   | Prices are always computed on the server; tampered client values can't change the amount charged                                                                                              | Met                                   | `tests/unit/acceptance-pricing.test.ts` › "server-side pricing under tampering": hotel (2 nights × ₹2,000 + GST; forged coupon or discount), cab, ride, food order (browser unit prices ignored), package quote. A forged expected total gets `price_changed` and nothing is written or charged. Also `tests/db/bookings.test.ts` › "rejects line items that do not add up to the totals", "ignores a captured amount that differs from the order"; `tests/db/packages-leads.test.ts` › "re-checks totals on save"; `tests/e2e/acceptance.spec.ts` › "tampered checkout links". |
| 4   | Double booking is impossible under concurrent requests                                                                                                                                        | Met                                   | `tests/db/acceptance.test.ts` › "double booking under concurrent requests": two holds racing for the last room, a rolled-back request leaving no hold, two orders racing for the last stock unit, two bookings racing for the last package seats, one trip per cab / ride booking. Each test checks the row lock or constraint inside the open transaction (`pg_locks`) and in the function source. Also `tests/db/bookings.test.ts` › "never sells more rooms than exist".                                                                                                     |
| 5   | Webhook replays and duplicate events don't create duplicate payments or bookings                                                                                                              | Met                                   | `tests/db/acceptance.test.ts` › "webhook replays and out-of-order events" (late `payment.failed` / `payment.authorized` after capture, failed attempt then successful retry, one refund across `refund.created` / `refund.processed` / redeliveries, a refund that later fails, one stored event id per provider); `tests/db/bookings.test.ts` › "confirms once however many times the payment is replayed", "de-duplicates webhook deliveries on the event id".                                                                                                                |
| 6   | RLS blocks cross-user and cross-vendor access (at least 2 users and 1 vendor)                                                                                                                 | Met                                   | `tests/db/acceptance.test.ts` › "RLS across two customers and two vendors": bookings, orders, prescriptions, vendor ledger, vendor documents, reviews (private columns hidden), privacy requests, travellers and addresses, for two customers, two vendors and a visitor; writes are refused or ignored; every table touched has RLS on. Plus `tests/db/rbac.test.ts` and the RLS tests in each module's database test. `tests/db/hardening.test.ts` checks pickup OTPs and hotel commission are outside the API grants.                                                        |
| 7   | Mobile Lighthouse ≥ 90 for performance, accessibility and SEO on Home and the hotel listing                                                                                                   | Partly met                            | Measured in Phase 11 without a database: home 84–89 performance, 100 accessibility, 100 SEO; hotels 85–92 performance, 100 accessibility, 91–100 SEO. | 9   | The docs let a new developer deploy from scratch in under an hour                                                                                                                             | Met                                   | `docs/DEPLOYMENT.md` §0–§5 (Supabase, Auth, first super admin, Vercel) and §16 (Phase 11 and go-live), `docs/ARCHITECTURE.md`, `docs/API.md`, `docs/ADMIN_GUIDE.md`.                                                                                                                                                                                                                                                                                                                                                                                                            |
